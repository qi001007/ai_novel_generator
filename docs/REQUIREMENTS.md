### 1.6 新建章节与简报（2026-09-02 主人重述需求后展开）

主人原话口径：**新建章节要像新建文件夹一样有显式入口**——要么右键打开新建，要么有新建
按钮，也可参考 VSCode 文件栏那种「一堆快捷键 + 右键」的形态。不是「点一下最新章节就自动
建下一章」（该理解已被否决）。

三通道入口（任一都能完成同一件事，共享同一个 store action）：

- [ ] v1 树底固定图标排 `新建章节`（UI-DESIGN 2.2 早已规定，一直未实现）
- [ ] v1 右键「单章简报」分组标题 → 菜单含 `新建下一章简报`
- [ ] v1 右键某个章节/简报行 → 菜单含 `在其后新建章节`（置灰并标注 P2，见下方插入代价）
- [ ] v1 全局快捷键 `Ctrl+Alt+N` = 新建下一章简报
- [ ] v1 空态：D 层无章节时显示「还没有章节」+ 内联 `新建第一章`

语义与边界：

- [ ] 新建 = **同时**创建 `Chapter(chapter_number = 现有最大 + 1)` 与 `briefs/{N:04d}.md`，
  二者章号必须一致；只建其一视为 bug
- [ ] 章号策略 v1 **只允许末尾追加**。中间插入要连带改简报文件名、B 层目录锚点章号、
  C 层弧的章节范围、已生成正文的 `chapter_number` 外键——漏一处即数据不一致，故列 P2
- [ ] 新建成功后：左树出现该章 → 自动打开该简报文件 → 光标落在 `## 目标` 行
- [ ] 不弹对话框收标题：`Chapter.title` 先留空，由简报内容反推标题回填列 P2
- [ ] 防重：请求未返回前入口全部 disabled，连点 5 次只建 1 章
- [ ] 后端 409（`ensure_chapter_number_unique`）时 toast 显示 detail 原文，不静默
- [ ] 后端不可用时点击给失败 toast，与底部「后端 已连接」状态条口径一致
- [ ] 刷新后新建的章节仍在（服务端单一真源，不接受前端伪造行）

验收：上述每条都要有对应测试或可复现步骤；`npm run build` 与前后端测试全绿。

## 9. 技术选型（2026-08-30 调研结论）

按 search-first 决策矩阵得出：优先采用成熟开源件，找不到合适积木的场景才自研。

### 采用（ADOPT）

| 场景 | 选型 | 依据 |
|---|---|---|
| 斜杠命令面板 + @引用选择器 | cmdk（~12.9k stars, MIT） | 无样式命令菜单，键盘导航完善，Codex 命令面板同类实现 |
| 双根树 | react-arborist（~3.7k stars, MIT） | 完整 React 树组件，支持折叠、虚拟滚动、选中态 |
| 正文编辑器 | TipTap（~38.2k stars, MIT） | 基于 ProseMirror，选区操作、装饰、批注原生可扩展 |
| 散文 Diff | diff（jsdiff）+ 自渲染 | 小说级段落对比不需要 Monaco 这类重量级代码 Diff 编辑器 |

### 待定（C2 架构评审决策）

- 组件基座：引入 shadcn/ui（Tailwind + Radix）替换手写 CSS，还是保留现有 `styles.css` 仅用上述积木库。涉及前端基建改造，归 C2 架构评审统一裁决。

### 自研（BUILD，无现成同类件）

- 双栏对照生成 + 逐段合并视图
- 内联审稿锚点 + 批注气泡（小说场景）
- A/B/C/D 双根树的数据模型层

### 同类项目参考

| 项目 | 定位 | 可借鉴 | 不采用 |
|---|---|---|---|
| Nigh/show-me-the-story（521 stars, Go+Svelte） | 自托管 AI 小说生成器，纲→逐章→审稿→伏笔→事实核验 | 流水线阶段可视化、全书润色批次 | Svelte 技术栈不可直接复用 |
| sigpanic/goink（193 stars, Wails 桌面） | 对话式写作 + 自动状态追踪 + 本地语义搜索 | 对话驱动 + 状态追踪的组合范式 | 桌面端架构不同 |
| SillyTavern（~32.8k stars） | LLM 前端，角色卡片生态成熟 | 人物卡片字段设计、卡片导入导出 | 面向角色扮演聊天，不是长篇工作台 |

调研结论：GitHub 上没有可整体照抄的"长篇小说工作台"Web UI，Codex/VSCode 混合范式即差异化方向，只取各家的积木与范式，不搬整套代码。

## 10. 上下文注入与可观测（2026-09-02 主人批注 5，**最高优先，后端不待帧**）

主人原话口径：分层管理与"各种设定如何合理注入上下文"是最核心最有创意的业务逻辑，
要兼顾成本、不忘关键内容、保证每章逻辑连续；担心实现乱做。
验收方式由主人指定：调成写作模式让 AI 写某一章时，**能在终端或某处看到本次续写实际注入的
上下文内容**，据此要求删块或加块，再改机制。

### 10.1 先修割裂（治本，PRD 6.1 已记录取证）

- [x] 取证：正文生成与对话 Agent 是两条通路，写作侧没有伏笔 / 人物状态 / 上一章结尾
- [ ] v1 正文生成改走与对话 Agent 同一个 collector 池（`collect_items()`），
  `build_draft_user_prompt()` 退化为渲染器，不再自行挑选资料
- [ ] v1 废除第二真源：`generate_from_brief` 取蓝图必须用 `documents._blueprint()`
  （最新 active 版本）；现状 `order_by(version)` 升序取**最旧**，属缺陷
- [ ] v1 对话侧 `build_context()` 与写作侧 `build_writing_context()` 共享预算常量与裁剪
  逻辑，只有排序规则不同
