# AI 网文生成工作台 PRD

版本：v0.4  
状态：自用已确认，随决策演进。设计理由与废止口径见 docs/DECISIONS.md（按 D-xx／X-xx 引用）  
定位：单机、自用优先的 AI 长篇连载生成与审稿工作台  

## 1. 产品判断

这不是一个面向大众的 AI 写作 SaaS，而是先解决作者本人的核心问题：长篇连载最容易崩的不是“生成不出一章”，而是设定漂移、角色失控行为、伏笔断裂、节奏崩坏，以及人工检查成本过高。

因此产品重心不是“全自动成书”，而是“分层规划 + AI 生成 + 机械校验 + AI 七维自检 + 人工终审 + 已确认事实回写”。系统必须让作者能稳定推进几百章，而不是让作者陷入重复整理设定和上下文的时间黑洞。

## 2. 用户与场景

- 主要用户：作者本人。
- 维护作品列表，进入某个作品后推进章节。
- 每天推进 1-3 章，每章 2000-4000 字。
- 开新卷、调整主线、回收伏笔时检查全局一致性。
- 作者给出新剧情反馈，希望 D 层立即调整，C 层局部调整，B 层选择性调整，A 层只做低频校准。
- 人工终审时直接编辑正文，而不是只能在编辑器外改完再粘贴回来。

不做：多用户协作、公开发布平台、全自动批量成书、复杂工作流编辑器。

## 3. 目标与非目标

### v1 目标

1. 提供作品列表；每个作品拥有独立的规划、设定、章节、摘要和审稿数据。
2. 完成四层规划：A 全书蓝图、B 目录章节序列、C 10-30 章剧情弧、D 单章简报。
3. 完成核心流水线：章纲 → 正文生成 → 机械校验 → AI 七维自检 → 人工终审 → 确认事实落库。
4. 使用 SQLite 持久化作品、规划、设定、角色、摘要、AI 结果与人工决定。
5. 支持按任务类型配置模型。实测四个：`draft`、`review`、`summary`、`chat`（`llm.py:44-47`）；`outline` 与 `fact_extract` 未实现。
6. 提供 Codex/VSCode 风格工作台：左侧规划与设定双根树、中间对话 Agent、右侧写作编辑器，支持正文直接编辑。
7. 每章保留可追溯记录：模型输入摘要、生成版本、校验结果、终审决定。

### v1 非目标

1. 不做多用户协作和权限系统。
2. 不做向量 RAG。上它的唯一合法前置：出现过一次可复现的「该给的章节没给」且确认是排序错而非未采集（D-12）。
3. 不做自动发布到小说平台。
4. 不做插件系统。
5. 不做 DAG / 工作流编辑器。
6. 不做全自动级联改写 A/B/C/D 规划。

## 4. 四层规划架构

规划必须分层，否则长篇会同时承担“全局约束不足”和“局部上下文爆炸”两个问题。

| 层级 | 名称 | 粒度 | 变更频率 | 作用 |
|---|---|---|---|---|
| A | 全书蓝图 | 最长期，全书主线、终局、核心冲突、主题 | 低 | 防止越写越散，是最高约束。 |
| B | 目录规划 | 章节顺序、章节名、每章承担的剧情功能 | 中 | 让章节序列在大背景下有起伏、反转和钩子。 |
| C | 剧情弧窗口 | 10-30 章小情节，主角完成一件事或下一次小副本 | 高 | 兼顾具体情节和连贯性，通常维护当前 + 后续 10-15 章。 |
| D | 单章简报 | 本章目标、事件、POV、出场人物、冲突、钩子 | 每章 | 直接服务正文生成。 |

规则：

- 四层规划的**唯一写入口**是文档层（4.4）。
- D 层必须可独立编辑。
- C 层是生成正文时的主要上下文，不做无限扩展。
- B 层是章节顺序和剧情功能的索引，可以滞后于 C/D 层，但不能长期矛盾。
- A 层是最稳定的低频约束，不应被单章反馈频繁重写。

### 4.1 C 层：弧是存储，滑动窗口是派生视图

主人 2026-09-02 批注：C 层作为滑动窗口，内容实时变更，究竟该用一个从头走到尾的 MD 承担，
还是定死 1~30 / 31~60 这种固定窗口，还是有更好的设计。三个候选的取舍：

| 方案 | 做法 | 结论 |
|---|---|---|
| a 单文件滑块 | 一份 `window.md` 随进度从头改到尾 | 否决。窗口即存储：推进一章就覆盖上一弧的计划，无法回查"写第 47 章时原本打算怎么走"；每次推进都改同一文件，提案 diff 与并发都难受 |
| b 固定章窗 | `1-30 / 31-60` 定死 | 否决。弧的长短是内容决定的（7 章收束或 40 章才收），固定边界会把一个弧劈成两半；窗口大小还被章号写死，与 token 预算绑在一起调不动 |
| c 弧对象 + 派生窗口 | 弧是存储单位，不定长、带状态；窗口在生成时现算 | **采用** |

采用 c 之后的规则：

- C 层存储 = 弧（`arc_plan`）：起止章、目标、冲突、收束、状态（未开始 / 进行中 / 已收束）。
  弧不随进度删除，写完只改状态，保留可回查。
- **滑动窗口不落盘**。每次生成第 N 章时现算，固定组成与顺序：
  `A 蓝图 → B 目录邻域（N±3 章） → C 当前弧（跨界时附上一弧收束摘要） → D 本章简报
  → 事实库（出场人物当前状态 / 未回收伏笔 / 上一章结尾）`。
  窗口宽度只受 token 预算约束：改预算不改存储，这一层就是成本与"不忘关键内容"的调节旋钮。
- 不变量：**未回收伏笔与出场人物状态永远在窗口内**，不靠窗口位置命中。这是长篇不失忆的底线。
- 窗口外的事实以**分层摘要塔**注入（章摘要 → 弧收束摘要 → 卷摘要），不是逐章原文。
  章摘要已有 `chapter_summary`，弧级与卷级摘要排在 Phase 3。

### 4.2 文件组织：树按章归组，DB 仍是唯一真源

主人的方案是"四层都在一个文件夹里管理，正文与 D 层规划同处一章目录"。方向采纳，
但必须先说清一个事实，避免假装照做：

- 现状 `blueprint.md` / `toc.md` / `arcs.md` / `briefs/NNNN.md` **不是磁盘文件**，
  是 `documents.py` 从 `planning_blueprint` / `toc_entry` / `arc_plan` / `chapter_brief`
  四张表现渲染的**投影**，写回时解析回列。真源是 SQLite，磁盘上并不存在这个文件夹。
- 所以"按章归组"落在**树的展示结构**上，零数据迁移：

```text
规划/
  blueprint.md      A 层全本蓝图（1 份）
  toc.md            B 层目录（列表视图，见 4.3）
  arcs.md           C 层弧序列
  chapters/         按章归组（主人要的"一章一个抽屉"）
    0042/
      draft.md      正文投影
      brief.md      D 层简报投影
    0043/
      draft.md
      brief.md
```

- 一章一目录、正文与简报同组，对后端只是路径解析规则变化，不动表结构。
- 旧路径 `chapters/{N}`（正文）与 `briefs/0042.md`（简报）继续可解析，不断链。
- 真磁盘文件（可 git、可手改、可备份）列为 P2 的**单向导出镜像** `exports/<书名>/…`，
  读仍以 DB 为准；双向同步要引入冲突解决，v1 不做。

### 4.3 B 层目录：以可搜索列表呈现，MD 退为源码视图

主人 2026-09-02 批注：目录只有 MD 纯文本形态，不方便搜索管理，也不好看；要做成列表并支持搜索。

- B 层的数据形状天然是表（章号 / 章名 / 剧情功能 / 备注），适合列表；A/C/D 仍是文档。
  这是 3.0「一切规划皆文档」的**唯一有意例外**：存储仍是同一张 `toc_entry` 表，改的只是视图。
- 默认视图 = 列表：可搜索、可按章号跳转、行内改章名与剧情功能、显示该章正文状态。
  「源码」开关切回 `toc.md` 文本视图。两种视图共用同一份数据与同一套锁规则（章号是主键）。
- 搜索 v1 做**本地全字过滤**（章名 + 剧情功能 + 备注，命中高亮、自动定位）；
  跨作品全文检索排 P2。

### 4.4 四层规划的写入口：文档层（B 路）

主人 2026-09-03 裁定，全量理由与新旧口径见 `DECISIONS.md` D-01 / D-02 / D-03。

- **唯一写入口** = `PUT /api/novels/{id}/files/{path}`。人改文档、AI 提案、新建章节，三种来源全走这一条。
- 该入口自带四道保护：小节标题与主键锁定（422）、`actor=ai` 字段白名单、`base_revision` 乐观并发（409）、
  提案稳定化（未改动小节逐字节不变）。
- `routers/planning.py` 的 POST/PUT 端点降级退役，只读 GET 按需保留。**禁止再开第二条写通路。**
- **DB 仍是唯一真源**：`.md` 是每次从列现渲染的投影，库里不存文档文本。选 B 路选的是「写入口」，
  不是「把真源搬进文件」。
- 为什么选文档入口：与已批准的 UI 范式一致（一切规划皆文档）；AI 改规划走「提案 + diff + 人点应用」时，
  文档比字段级 PATCH 更容易让人读懂改了什么。
- 代价（已知并接受）：`/planning/*` 那 9 个端点退役、`store/workbench.ts` 的新建章节改走文件层。
  排期为 S3，且**必须早于 S2**——Agent 的管理规划命令若绑在两条通路上，等于把双真源自动化放大。

## 5. 剧情反馈系统

作者反馈不应直接覆盖全部规划层，而应先进入影响分析，再由作者确认要改哪些层。

```text
作者反馈
  → 影响分析：判断影响 D / C / B / A
  → 生成建议修改
  → 作者确认
  → 更新对应层
  → 记录规划版本
```

影响规则：

- 单章节奏、视角、事件微调：优先影响 D。
- 小情节走向、后续 10-15 章节奏、角色目标变化：影响 C，可能连带 D。
- 章节顺序、章节名、重要反转位置变化：影响 B，可能连带 C/D。
- 主线终局、核心冲突、主题变化：影响 A，必须人工明确确认。

v1 不做自动级联改写。系统先给出建议和影响范围，作者确认后才更新。这样能节约 token，也能避免作者只改了一个细节却把全书蓝图改乱。

## 6. 核心流水线

```text
D 章节简报
  → 正文生成
  → 机械校验：字数、禁用词、黑名单、必要字段
  → AI 七维自检：一致性 / 角色行为 / 节奏 / 连贯 / 伏笔 / 钩子 / 文风
  → 人工终审：通过 / 编辑后通过 / 打回重生成
  → 事实落库：章摘要、角色状态、关系变化、伏笔状态
```

规则：

- 章节状态只前进，唯一显式回退是“打回重生成”。
- 只有“确认通过”后的内容才会更新事实库。
- AI 自检做完整七维，但每条结论必须引用原文证据；没有证据的结论只算提示，不算评分。
- 人工终审允许直接编辑正文；编辑后保存为新版本。
- 每章显示 token 用量与成本估算。

### 6.1 上下文注入：一个构造器，一份可查清单

主人的要求（2026-09-02 批注）：调成写作模式让 AI 写某章时，要能在终端或某处看到
**本次续写实际注入了哪些上下文**；觉得多余就让机制删，觉得缺就让机制加。

先记录一个必须治本的真实缺陷：系统里有两套互不相通的上下文通路。

| 通路 | 代码 | 实际注入 |
|---|---|---|
| 对话 Agent | `services/chat.py` → `build_context()` | 全量：预算裁剪、相关度排序、@引用 |
| 正文生成 | `routers/chapters.py` → `build_draft_user_prompt()` | 只有 novel / blueprint / arc / brief 四个对象 |

后果：`/generate` 写正文时**没有伏笔、没有人物当前状态、没有上一章结尾**；
而且它取蓝图用 `version` 升序第一条（最旧版本），与对话侧"取最新 active"相互矛盾。
同一个"上下文注入"存在两条实现，之后必然继续漂移。

治本方案：

1. **单一构造器**：正文生成改走 `build_writing_context()`，与 `build_context()`
   同库同 `collect_items()`，只是排序规则从"问题相关度"换成"写作优先级"（见 4.1 的窗口组成）。
   `build_draft_user_prompt()` 退化为渲染器，不再自己挑选资料。蓝图读取统一走
   `documents._blueprint()`（最新 active 版本）。
2. **注入清单双通道可观测**：
   - 终端：`NOVEL_CONTEXT_DEBUG=1` 启动后端，每次生成打印清单
     （序号 / 层级 / 标签 / 字符数 / 是否被预算裁掉及原因），主人边跑边看。
   - 落库：`generation_run.input_summary` 存结构化 JSON 清单，
     `GET /api/novels/{id}/chapters/{chapter_id}/generation-runs` 可回读，
     按 7.4 的独立详情页范式展示。
3. **迭代回路**：清单每一项都带 `kind`（blueprint / toc / arc / brief / setting /
   character / foreshadow / summary / chapter）。主人指哪个 kind 该删或该加，
   只改对应 collector，不改调用方，也不改提示词模板。

## 7. 设定库

设定库不是静态百科，而是“随章节演进的事实系统”。

### 7.1 基础实体

- 世界观：规则、力量体系、历史、禁忌、重大事件。
- 地点：位置、归属、功能、当前状态。
- 势力：目标、关系、层级、当前状态。
- 物品：用途、归属、限制、状态。
- 伏笔：内容、埋设章、预计回收章、状态。

### 7.2 人物卡片

人物采用卡片管理，并支持动态分级：

| 级别 | 典型跨度 | 用途 |
|---|---|---|
| 主角团 | 全书或长期 | 深度档案、目标、关系、行为约束。 |
| 重要配角 | 多卷或长剧情弧 | 关键动机、关系变化、重要事件。 |
| 小 Boss / 剧情弧反派 | 10-30 章 | 本章弧内的目标、威胁、结局。 |
| 龙套 / 功能角色 | 1-几章 | 基本身份、功能、退场方式。 |

人物分级不必与章节严格绑定。例如长期人物可以很晚才出现，龙套也可以跨几章。系统应记录“预计出现窗口”和“实际出现章节”，当实际使用明显偏离预期时提示作者确认。

### 7.3 世界观地图

世界观地图支持后续调用生图模型生成图片。v1 可以先存位置卡片和关系，图片生成放在设定库稳定之后。

生成地图时必须遵循：

1. 只使用已确认的设定事实。
2. 生成结果标记为“参考图”，不是事实来源。
3. 作者确认后才能关联到对应地点卡片。

### 7.4 绘画详情：独立页面，不做底栏

主人 2026-09-02 批注：详情做成底栏形态不推荐，最好是一个能单独打开的页面，
显示消耗 token 以及一些其他信息。

- 独立整屏路由 `/novels/:id/artworks/:artworkId`，打开时**替换整个工作区**，
  不再嵌在右栏或底部条带里；顶栏只保留返回面包屑。
- 页面必须显示：结果大图、提示词、生成历史与版本对比，以及**本次调用的成本事实**——
  模型、输入/输出 token、耗时、成本估算，数据源 `generation_run`。
- 同一范式适用于正文生成详情：任何一次 AI 调用都要能在自己的页面上看到
  token 消耗与注入上下文清单（6.1）。

## 8. 数据范围

v1 至少需要：

- `novel`：书名、简介、目标篇幅、文风约束。
- `planning_blueprint`：A 层全书蓝图。
- `toc_entry`：B 层目录项、顺序、章节名、剧情功能。
- `arc_plan`：C 层剧情弧、起止章、目标、冲突、状态。
- `chapter_brief`：D 层单章简报。
- `chapter`：章号、标题、状态、正文、终审结论。
- `setting`：世界观、势力、地点、规则、禁用事实。
- `character`：姓名、级别、身份、目标、关系、当前状态、预计出现窗口。
- `character_appearance`：人物实际出现章节。
- `foreshadow`：伏笔、埋设章节、预计回收章节、状态。
- `chapter_summary`：章摘要、事件、状态变化、关联伏笔。
- `plot_feedback`：作者反馈、影响层级、建议修改、确认状态、应用时间。
- `generation_run`：任务类型、模型、prompt 版本、输入摘要、输出、token、成本。
- `review`：AI 自检结果、人工评论、决定、时间。

## 9. MVP 切法

### Phase 1：UI 骨架与核心写作环

1. 书架首页（封面卡片墙 + 新建向导）。
2. 工作台三栏布局与双根树（规划 / 设定库）。
3. A/B/C/D 四层规划的基础编辑。
4. CodeMirror 6 编辑器（原 TipTap 选型作废，见 X-04）：双栏对照生成、选区 Diff 修改、内联审稿、Ctrl+F、自动保存、版本历史。
5. 字数、禁用词、黑名单、必要字段机械校验。
6. AI 七维自检，要求引用原文证据；审稿意见内联锚定正文。
7. 对话 Agent：斜杠命令、@引用、流式消息，与写文 AI 分离配置。
8. 人物卡片 v1（分类标签、搜索、详情弹层）。
