### D-18 模型的推理单独存一列，绝不混进 `content`

- **结论**：`chat_message.reasoning` 保存模型自己的推理（迁移 `f3b9c0d21a55`），
  界面上是回答上方一个默认收起的折叠。它**不是** `content` 的前缀，也不进
  `_history_messages()` 与注入上下文。
- **为什么不并进 content**：`content` 会被回放成后续对话的历史、并被 `collect_items()`
  当资料注入。推理一旦混进去，模型下一轮就会把自己上次的心里话当成"已经说出口的话"
  再讲一遍，甚至据它作答——那是最难查的一种自我污染。
- **取法**：`stream_messages` 用 `reasoning_out` **出参累加器**收集 `delta.reasoning_content`
  （兼容 `delta.reasoning` 这一写法），与既有 `usage_out` 同一形状。
  没有改 `Iterator[str]` 的 yield 契约——那会波及 draft / reviews / planning 等全部调用方，
  而它们中的绝大多数根本不需要推理。
- **拼接口径**：累加器收到的是**增量块**，相接不加任何分隔；段落分隔只发生在
  **agent 跨步骤**之间。第一版把每块都用 `\n\n` 拼，真机上推理碎成了
  「用户\n\n想\n\n让我」——这条由 `test_agent_loop.py` 钉住。
- **出参必须显式带上**：`ChatMessageOut` 与 `_MESSAGE_FIELDS` 都要有 `reasoning`，
  否则流式那一次能看到、刷新后入口消失（本条落地时就漏过一次，已补测试）。

### D-19 附件是「本轮的上下文」，不是服务器上的文件

- **结论**：聊天附件由浏览器读成文本，随该条消息发给后端，变成 `ContextItem(kind="附件",

### D-23 删除是物理删除，一条事务，14 张表按「子先父后」；不做回收站

D-22③ 授权后的具体策略。

- **端点两条**：`DELETE /api/novels/{id}` 与 `DELETE /api/novels/{id}/characters/{cid}`，
  都返回 **204 空体**（没有东西可回；`api.ts` 的 `request` 原先无条件 `json()`，
  会把一次成功的删除报成「Unexpected end of JSON input」，已加 204 分支）。
- **级联清单在路由里显式列全 14 张 novel scoped 表**，不靠 DB 的 `ON DELETE CASCADE`：
  现有表没有外键级联声明，要靠 ORM 级联就得给 15 张表补 relationship；
  显式列表能读、能测（测试逐张数到 14 行、删完再数一次为 0），顺序写错会当场炸。
  顺序：`character_appearance` 先于 `character`、`chapter` 先于 `chapter_brief`
  （`chapter.brief_id` 指着它）。`app_config` **不参与** - 它是全局偏好（D-16 / D-21），
  不属于任何一本书。
- **不软删**：库里没有任何 `deleted_at` 列，加一列要改每一处查询；这是单人本地应用，
  PRD §2 要的安全是「把书名原样打一遍」那一步，不是一个谁都不会去清的垃圾桶。
  ~~界面照办：右键 → 删除作品… → 输入书名~~ —— **这条界面口径已被第二十四批批注 1 推翻**
  （主人：「我右键哪本书点删除，肯定是指删除对应的这本书」）。现在是弹窗一次确认、
  焦点默认在「取消」、删完即消失；**不软删**这个决定本身没变，变的是那一步打字。
  「不软删」之所以还成立，是因为备份那条已经排进下一步第一位（D-27）。
- **归属必须一起验**：`DELETE /novels/{a}/characters/{b}` 里 b 不属于 a 时是 404，
  不是把 a 之外的行删掉。这是 T-18（两个 id 拼出的操作要能证明属于同一本书）的删除版。
- **仍然未开放**：删章节、树里文件重命名。章号是主键（D-11），
  删一章/插一章要回答「后面的章号要不要顺延」，那是 D-13 未决的产品语义。
- **真机证据**：建一本书 → 用 `settings/characters/new.md` 那扇门建人物（投影 200）→
  `DELETE /characters/7` 得 **204 空体** → 人物列表 0、文件列表里没有该路径、
  投影 **404**（D-02：行没了投影自然没了，不需要第二条写通路去「删文件」）→ 删掉这本书 204。
  验证用的两本书都已清掉，作品库回到原有 6 本。
- **没替主人做的**：`dbg`（id 6）与 `MD探针`（id 3）两个误建作品**我没有删**。
  计划里写着「等端点补齐后删除」，端点补齐了，但删他库里的行是另一个动作 -
  现在那扇门开着，他在书架上右键、把书名打一遍即可，两本书各五秒。

### D-26 `.md` 投影层保留，但从「目录」降级为「一种可导出的通用格式」（2026-09-06）

主人问：既然文件栏里的 `.md` 是虚拟生成的、真实存储不是这个样子，那
「正文正常渲染、草稿用 MD 呈现」这一层转换还有必要吗？草稿是不是也别用 MD、直接渲染？
授权我定，所以我定，并把能反驳自己的理由写下来。

**裁定：这一层留着，但它的定位改了。**

- **真源不动**：数据库仍是唯一真源（D-02 不变）。这一条不参与讨论。
- **为什么不能删这层**（三条，第三条最硬）：
  1. Markdown 是**模型读写的那一种格式**。Agent 的提案、机械校验读的东西、
     注入给模型的资料，全是按这份投影的语法在切的（D-10 的键锁：结构锁、值可改、AI 白名单）。
     删掉它，就得为「AI 要改哪一段」另发明一套私有格式 - 代码更多，主人得到的更少。
  2. 它是**能带走的格式**。第二十四批把导出做出来之后，右键导出的就是这些 `.md` 与 `.txt`；
     「虚拟」的抱怨，一半其实是「我拿不到手」，导出把这一半解决了。
  3. **删掉表示层不等于删掉风险**。同一件事有两种表示确实会互相覆盖（本项目真丢过字），
     但解法是「只有一个真源 + 只有一条写入口」（已经是 D-01/D-02），
     不是「只留一种表示」 - 后者会让草稿变成只能在网格里改的字段，
     写长篇的人最恨这个。
- **为什么草稿也不改成「直接渲染」**：正文是连续长文，连续文本编辑就是对的形态；
  渲染面是**读**的那一面。两面都留，默认落在渲染面，源码面按需切（这条已经是现在的行为）。
- **该改的是界面上的口气**：文件栏**不是磁盘目录**，磁盘上没有这些文件。
  `WORKSTREAM-PLAN §一` 那句话照这个改；不打算把 `draft.md` 改名成「正文」-
  它现在是一个真会导出的文件名，名字对上比名字好听有用。
- **判据（怎么算这条落地了）**：文档里不再有任何地方把文件栏说成「目录」；
  §一 明写「磁盘上没有这些文件」；导出功能在（24.4 已交付，是这条成立的前提）。

- 后端 `routers/novels.py` 只有 GET／POST／PUT。
- 而 PRD §2 与 UI-DESIGN §1 功能点都明文要求「删除作品（输书名确认）」。

为什么不顺手补：删一部小说要先定 15 张表的级联策略（`chapter`／`chapter_brief`／`chat_message`／`generation_run`／
`foreshadow`／`review` 是物理删还是随 novel 软删），还要设计二次确认交互与帧。这是业务逻辑，不是清理。
已登记进 REQUIREMENTS §1 与 WORKSTREAM U7，排在 S3 之后。

## 6. 文档职责（改文档时照这个分工，别再往一处堆）

| 文件 | 只装什么 | 明确不装什么 |
|---|---|---|
| `AGENTS.md` | 工具纪律、回答习惯、**项目架构红线**（一句话级别、违反即错） | 架构解释、进度、历史 |
| `docs/ARCHITECTURE.md` | 真源与写通路、模块**实际**完成度、S0–S3 主干 | 需求条目、视觉规格、为什么这样定的理由 |
| `docs/PRD.md` | 需求与验收标准 | 文件路径实现细节、进度、理由历史 |
| `docs/REQUIREMENTS.md` | PRD 的功能拆解勾选 | 设计令牌、架构决策 |
| `docs/UI-DESIGN.md` | 视觉与交互规格 | 后端契约、进度 |
| `docs/WORKSTREAM-PLAN.md` | **唯一的进度入口**，说人话：已经能用的 / 还差什么 / 下一步顺序 / 需要主人点头的事 | S・U 编号组织法（第二十三批删）、已完成流水表（结论在提交信息与本文件）、后端契约（去 ARCHITECTURE） |
| `docs/UI-BACKLOG.md` | **未完成条目的可勾选清单**，做完一条勾掉并把结论写进 WORKSTREAM-PLAN | 已完成的历史、理由、视觉规格 |
| `docs/HANDOFF.md` | 开新对话所需的最小信息：环境、验证命令、指向 | 上面任何一类的正文 |

一句旧账：「AI 不自觉补后端」的根因不是模型手贱，是**没有任何一份文档写着「不许新增写通路」**。
每场新对话读的是 HANDOFF + WORKSTREAM-PLAN，而那两份当时在讲 YAML 和帧审批。
