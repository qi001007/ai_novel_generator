## 1. 决定

### D-01 规划写入口只有文件投影一条

状态：生效。A/B/C/D 与文本设定只经 PUT /api/novels/{id}/files/{path} 写入；/planning/* 写路由只保留 410 退役桩。任何新规划能力必须复用该入口。

### D-02 SQLite 是唯一真源，Markdown 是投影

状态：生效。数据库存结构化列，Markdown 每次现渲染并解析回列。磁盘双向同步会引入冲突解决，v1 不做。

### D-03 正文与简报按章归组

状态：生效。规范路径为 chapters/NNNN/{draft.md,brief.md}；旧路径可读，新写只用规范路径，不做数据迁移。

### D-04 上下文只有一个资料池

状态：生效。collect_items() 是唯一采集入口；对话与写文只允许排序不同。新增资料改 collector，不在调用方拼提示词旁路。

### D-05 弧是存储，窗口是派生视图

状态：生效。剧情弧保留起止章与状态；生成时按目标章和预算计算窗口。不得用固定 1–30/31–60 文件或覆盖式 window.md 取代。

### D-06 注入清单必须可观察

状态：生效。终端调试与 generation_run.input_summary 使用同一清单，展示来源、字符数、档位、裁剪与原因。空块不能伪装成已注入。

### D-07 前端网络边界只在 api.ts

状态：生效。组件、页面与 store 不直接 fetch；离线演示如需 fixture，也实现同一 API 契约，不复制一套前端。

### D-08 编辑器采用 CodeMirror 6

状态：生效。TipTap 方案废止。编辑器扩展与文档结构识别围绕 CodeMirror 维护。

### D-09 D 层标题不重复章名

状态：生效。章名只归 B 目录；D 层标题只说明章号与“单章简报”，避免两个字段互相覆盖。

### D-10 文档结构锁定，AI 受字段白名单限制

状态：生效。小节标题、记录主键和文件章号不可任意改；actor=ai 只能修改明确字段且不能增删记录。结构变化必须走专用的人类动作。（「不能增」一半由 D-39 作废，本条其余部分继续生效。）

### D-11 AI 提案在展示 diff 前稳定化

状态：生效。未修改小节必须恢复为原文，防止模型重排整篇制造噪声；合法值修改仍由后端结构校验。

### D-12 v1 不做向量 RAG

状态：生效。只有出现可复现的“资料已采集但排序没给到”，且 SQL/规则排序无法解决时，才重开向量检索。

### D-13 “只允许末尾追加”已被 D-29 取代

状态：已废止。当前支持末尾追加、指定章后腾位和删除后顺延；全部章号引用必须由 renumber.py 一次搬齐。

### D-14 新建章节必须有显式入口

状态：生效。按钮、菜单或快捷键共享同一 action；不得以“点击最新章自动创建”代替。创建必须同时得到章节与简报。

### D-15 文本设定与人物档案并入文件投影写口

状态：生效。人物档案使用 settings/characters/{id}.md；头像是资产，走窄端点。世界观与伏笔使用各自文本投影。反馈分析保持专用流程，v1 不为它强开第二份可编辑投影。

### D-16 LLM 运行配置存数据库

状态：生效。app_config 是运行期真源，.env 只作首次种子与兜底；空值也覆盖兜底。密钥只写不读，连通测试不发计费 completion。

### D-17 2026-09-05 三项授权已关闭

状态：关闭。保留人物卡组件；推理单列由 D-18 管；历史控制块脏行已按备份后删除处理。此条不再承载新决定。

### D-18 推理与正文分列

状态：生效。chat_message.reasoning 不拼进 content，也不作为下一轮历史正文。对话流可单独展示 reasoning，其他 LLM 调用的流契约不因此改变。

### D-19 附件只属于本轮上下文

状态：生效。浏览器读取文本并作为 ContextItem 进入同一清单；不上传、不落盘、不进入下一轮。后端再次校验类型、数量和字符上限。

### D-20 供应商列表与任务路由分离

状态：生效。供应商保存连接信息，draft/review/summary/chat/image 路由选择供应商与模型；不为每个任务复制一套连接配置。

### D-21 外观偏好只存浏览器

状态：生效。主题、强调色、字体和字号属于这台机器，通过 appearance store 与 html data 属性单点写入，不进入 app_config。

### D-22 2026-09-06 六项授权已关闭

状态：关闭。对比度、顶栏按钮、删除语义、required_facts 机械口径、隔离 live 冒烟和生图槽位已分别落到实现或 D-23/D-24。此条不再充当进度表。

### D-23 删除采用事务内物理删除，删除前快照

状态：生效。作品删除显式清理 14 个作品子模型后删除 novel（共 15 张作品相关表），app_config 不参与。章节与人物删除验证归属；所有破坏性动作先快照。不做全库软删。

### D-24 无图片权限时生图保持未启用

状态：生效。当前配置的 key 只能调用 LLM/Embedding；图片请求曾返回 401。更换并验证有图片权限的供应商前，不展示可执行的生图假按钮。

### D-25 脚本调用 FastAPI 依赖时显式传 session

状态：生效。Depends 默认值只在 FastAPI 注入链有效；手动脚本必须自己建立并传入 Session。离线分支通过不能证明 live 分支有效。

### D-26 Markdown 是投影与导出格式，不是磁盘目录

状态：生效。它同时服务人类编辑、AI 提案、结构锁和可携带导出，因此保留；界面与文档不得把虚拟文件树描述为真实磁盘目录。

### D-27 简化删除确认后必须优先补恢复能力

状态：已完成并由 D-30 接管。确认不要求输入书名，但默认焦点在取消；删除前快照与恢复入口是这项简化的安全前提。

### D-28 Agent 循环迁移到 Pydantic AI

状态：进行中。循环、预算、参数校验与多工具执行交给 Pydantic AI；项目保留网关适配、只读工具、提案协议和产品边界。NOVEL_AGENT_ENGINE=pydantic 才启用新路，默认 legacy。切默认前补同参数去重、跑双引擎契约与真网关冒烟；验收后再删 legacy。

外部框架不得接管数据库历史、collect_items() 或外部遥测。直接依赖固定版本，传递依赖风险单独治理。

### D-29 章号是位置，章名属于 B 目录

状态：生效。插入后章号增加、删除后减少，章名随内容移动且只写 toc.md。所有带章号引用的表由 renumber.py 的集中清单搬移，禁止散落更新。

### D-30 快照记录范围，恢复一章是一个动作

状态：生效。快照 reason 必填；列表按真实时间排序并结合活库判断可执行动作。恢复一章一次带回简报、正文与目录行，且保留用户在快照后对其他章节的修改。

### D-31 有首条用户消息才算历史对话

状态：生效。历史列表由后端分组判定；空线程不显示，前端不乐观伪造第二套列表。

### D-32 章号压缩只能由主人确认触发

状态：生效。先展示逐行改号与弧范围报告，再快照，再按主人动作执行；禁止启动时自动迁移用户章号。

### D-33 UI 断言保护决定，不绑定源码位置

状态：生效。逻辑搬家时可修改断言的定位方式，但不能减少决定覆盖；必须用一次反向变异证明断言会在决定被破坏时失败。

### D-34 界面 kind/task 词表只有 labels.ts

状态：生效。A 层统一叫“全书蓝图”；组件不得各自维护 TASK_LABELS/KIND_LABELS 或时间格式化副本。

### D-35 投影语法表只有后端 _GRAMMAR

状态：生效。后端随 FileDoc 发布按 kind 的 grammar，前端据此识别结构和字段；测试 fixture 也从后端语法生成，禁止第二张人工标签表。

### D-36 写作上下文采用 B/C ±20 与“仅上一章全文”

状态：已决定，待实现。B 与 C 对目标章使用前后 20 章窗口；B 只带摘要字段。上一章简报和完整正文为必给，其他章正文禁止进入。世界观不整体升为必给，只有明确引用项优先；依据是现有 12000 字预算在长篇规模下已接近上限。

### D-37 Agent 通过确认动作卡触发现有生成链

状态：已决定，待实现。Agent 只定位目标章并形成动作卡；主人确认后由应用调用现有章节流式生成端点。不给 Agent 任意文件写工具，不另开规划写口；取消、刷新和重复点击必须幂等。

### D-38 确认后的首次 B/C 提案可初始化空投影

状态：生效。`actor=ai` 只表示主人已在提案卡上点击应用，不表示 Agent 获得自主写权限。空的 `toc.md` 或 `arcs.md` 没有可保护的主键，因此首次确认允许创建记录；非空文件曾按 D-10 一并拒绝增删与改号，「拒绝增」一半由 D-39 作废。这样保留单一 PUT 写入口，也避免把初次规划错误地当成 AI 结构篡改。

### D-39 AI 提案可追加记录，主键由系统分配（推翻 D-10 的「不能增」）

状态：生效。2026-09-09 主人在批次 35 裁定：「我在对话框里输入，这个对话 Agent 就能实现我人工操作的所有功能」，并选定口径「允许新增，且自动建章节本体」。据此：

- **可增**：`actor=ai` 的提案可追加记录。C 层用 `## 弧 ? 标题` 表示主键待分配，由文件层分配 `max+1`；B 层用文件里没有的 `## 第 N 章`。D-10「不能增删记录」里的**「不能增」一半作废**，「不能删」一半继续生效。
- **不可删、不可改号**：删除既有条目、改动已有主键仍按 D-10 拒绝。B 层的「删 5 加 6」就是改号，必然命中删除分支。
- **B 层新增即建章节本体**：`_write_toc` 追加新章号时同时建 `Chapter`（`brief_id` 允许为空），使左侧树与人工新建一致；建 `TocEntry` 的**两条**分支（已有条目的 `actor=ai` 追加、空目录或人类的全量写）共用同一次 `_ensure_chapter`，35.13 才把这条裁定落全。`_write_brief` 仍是另一处建本体，两处都在唯一 PUT 写入口内，不开第二条通路（D-01 不变）。
- **承诺必须实现**：写入层三处（`_resolve_ids` 的 surrogate 分支与两条 `_*_writer`）与提示词的「`?` 由系统分配」文案曾各写各的，实现却在零处。本条之后以写入层的真实分配为准，文案不许再许诺代码做不到的事。
- **判定只有一处**：主键配对由 `_resolve_ids` 一个函数裁定，预览（`chat.extract_proposals`）、提案工具闸门（`proposal_actions._gate`）、写入层三条 `_*_writer` 共用。闸门必须拿到当前文件（`documents.current_text_reader`），否则它会发出一张预览必拒、按下去什么都不发生的卡。**文案也只有一处，且必须指出下一步**（35.14）：只说"不能做什么"，模型就拿同一条负载再撞几轮——实测一句「新增一条剧情弧」在 `propose_arcs` 上空转四轮，直接吃满 35.9 的预算。
- **改号在成卡之前还原**：`stabilize_proposal` 按当前文件把主键写回去，所以「第 42 章改成第 99 章」产出的是一张**不改主键**的卡；写入层对原始文本仍然 422。还原发生在提案侧，不在文件侧开后门。

### D-40 五类规划只有一条提案通道

状态：生效。批次 35.8 裁定：A 蓝图 / B 目录 / C 剧情弧 / D 简报 / 新建人物**只能走各自的 `propose_` 动作工具**；手写整份文件的代码块只留给没有类型动作的对象（伏笔、世界观、改已有人物卡）。提示词里不许再出现「用工具还是手写都可以」这类等价表述。

- **依据**：那句等价表述就是第二条通道。作品 6 的真实流量里模型一次都没调用过 `propose_*`，全部手写并自造字段名（起止章 / 背景事件 / 悬念钩子），四张卡三张红。2026-09-10 同一份 C 层请求在装好写法表后重放，trace 是 `read_file(arcs.md)` → `propose_arcs` ×4，模型开始照抄文件里的 `arc: 4` 主键。
- **写法表与校验同源**：`markdown_doc.grammar_text(kind)` 与前端用的 `grammar_for_kind` 读同一张 `_GRAMMAR`（D-35），由 `agent_tools.read` 附在文件正文之后；提示词不抄字段名，抄一份就会漏改一份。

### D-41 对话模式由这句话指向的对象裁定

状态：生效。批次 35.10 裁定：`plan` / `write` 不再由 composer 上那个手动开关单独决定。`chat.effective_mode(text, requested)` 先读这句话——点中成稿词（正文 / 续写 / 扩写 / 往下写…）走 `write`，点中规划对象（简报·目录·剧情弧·人物·蓝图，含「A/B/C/D 层」与四个真文件名）走 `plan`，两边都没点中才照拨的开关；成稿词优先。

- **依据**：主人的批注是「我让他生成 D 层的 brief 简章，他却去给我生成正文内容」。`mode` 默认 `"write"`（`routers/chat.py` 的请求模型、`ChatPane.tsx` 的 `useState`），提示词体取 `SYSTEM_BODIES[mode]`，而 `WRITE_BODY` 第一条就是「主人要正文时直接输出可用文字」，整段不提 D 层也不提 `propose_chapter_brief`。开关本身没坏，坏的是"模式与这句话无关"。
- **判定只有一处、下游共用**：`prepare_turn` 判一次，`_system_prompt` 的模式体、`temperature_for`、注入日志的 note、落库的 `mode` 全读同一个值；两个引擎（D-28）走同一条装配，不存在 legacy 按计划、pydantic 按写作。用词表而不是再问一次模型：多一次请求就多烧一份 35.9 的预算，而表可以被测试逐行反查。
- **对称**：开关拨到 `plan` 而主人说「把第 3 章正文写出来」同样改判 `write`，否则 `PLAN_BODY` 的「禁止输出章节正文」会变成另一个"要不到正文"。表驱动测试两边都跑。
- **已知未修的界面缺口**：composer 仍显示主人拨的那一侧，而本轮实际按判出来的模式跑。数据是真的（消息行与 `context` 事件都带 `mode`），只是显示层没接。登记在 UI-BACKLOG 35.15，本轮不改界面。

### D-42 对话 Agent 单轮预算由主人设定，只有一个读取点

状态：生效。批次 35.9 裁定：`max_steps` / `max_tokens` 不再是源码里的常量。出厂值 `6 轮 / 60000 token` 按作品 6 实测的一轮给出，两个数在「设置 → 模型接入 → 对话 Agent 预算」里改，保存即生效；读取点只有 `agent.resolve_config(session)` 一个，文案只有一句 `agent.budget_hint(...)`。

- **依据**：30000 卡住的正是产品要求的那一轮，不是失控。每次模型请求都把增长后的整段上下文重新计费，所以一轮的成本 ≈ 请求数 × 上下文长度；作品 6 一句「新增一条剧情弧」新会话跑满 6 个请求是 32955 token，带上主人真实历史第 5 个请求就 35545。原话证据在 UI-BACKLOG 35.9 的复现行（`31623 / 30000（第 4 轮）`）。
- **60000 不是拍脑袋**：实测那一轮的 32955，加上历史窗口取满（8 条消息 / 4021 字符，比测得那轮的窗口长）时 6 个请求多出的约 17000。`test_the_measured_plan_turn_fits_under_the_default_ceiling` 把这条算式钉住，改默认值必须连它一起改。
- **不做 `.env` 覆盖**：那会造成第二个真源，还要再定"谁赢"。设置页存 `AppConfig` 行（D-16），与本页其余项同一条 GET/PUT、同一个保存按钮，读回即当前值。
- **护栏只防手滑，不防主人**：`MAX_STEPS_LIMITS (1,20)`、`MAX_TOKENS_LIMITS (1000,1000000)` 之外 422；库里存进一个不是数字的行则回落默认值而不是把对话弄瘫（`test_a_hand_edited_row_that_is_not_a_number_falls_back`）。
- **与验收判据的差异要记下**：35.9 原句写「改配置后重启生效」，实现是存库立即生效、不需要重启——比判据更强，且与设置页其余项一致。

### D-43 重新生成的 C 层围栏：省略的字段从档上继承，已应用过的重读即收起

状态：生效。批次 35.1 裁定。模型整本重写 `arcs.md` 时只改「目标」、把其余五个字段省掉，是合法形状而不是错误：`_align_arc_history`（`documents.py`）把每一条省略掉的 bullet 无条件回到**它落到的那条档上记录**的原值，`弧 N` 主键与起止章一寸不让；一条围栏已经落库之后，书比围栏多出一条，此时允许围栏里 `弧 ?` 那块按**起止章完全相同**绑到档上那条，整份围栏还原成文件本身，`legacy_proposal_matches` 认出来、前端把卡收起。

- **依据（真机 A/B，不是推理）**：同一份围栏、同一份库副本，只换代码。HEAD 那台（8031）卡是红的、按钮 disabled、aria-label 写「不可应用：「弧 1 觉醒·逃亡」 的小节标题与字段名是结构标识，不可增删改名：缺少 起始章、结束章、冲突、收束、状态」，PUT 一次都没发出——正是主人那句「这个按钮按不了是为什么」。修好的那台（8032）卡可点、PUT 200、弧 4/5 主键与 1-5/6-10 起止章不动、档上那段长「冲突」原文回到文件里、新弧按系统分配的 7 落库，刷新后卡不再出现。
- **不放宽结构校验**：继承发生在提案侧，PUT 侧的校验器一行没让。少一条仍然是删除，仍然 422（`test_dropping_an_arc_is_still_refused_after_the_inheritance_fix`）；`弧 ?` 绑不上就是真追加，走追加那条路径。
- **绑定的唯一凭据是起止章**：不做标题模糊匹配、也不按位置猜——位置兜底只用于「编号记录数与档上记录数已经相等」这一种（35.2 起这个"相等"按 D-44 改成「绑定后剩下的档上记录数」），追加块必须有确切起止章才认。
- **判据末条「刷新后红字 0」逼出来的第二半**：只修第一次应用，红字会随刷新回来（书已经长出第三条，块数≠现有数又回到整段放弃的老路）。所以这一条判据实际钉住了两个形状，两个都有测试。

### D-44 从 B 层改道出来的弧认档不认块数；`弧 ?` 永不回查已有行

状态：生效。批次 35.2 裁定。主人在作品 6 贴一条带范围标题的 B 层围栏（`## 第 11-30 章 弧 3：门钥之谜` 之类）说「按这一份更新」，抽提案时范围标题整段改道进 C 层——这一步 HEAD 已经做了，卡却点不动：PUT 回来 `422 AI 只能改这些字段：title, objective, conflict, resolution, status；以下受保护字段被改动：start_chapter, end_chapter（arc 7）`，一条弧都没写进去；好不容易落库之后重读同一条围栏，卡片又把那 7 条弧列成 `弧 ?` 再给一遍，第二次应用把 9 条变成 16 条。四处各定一条：

- **`弧 ?` 不回查已有行**：投影里的 `弧 N` 就是 `ArcPlan.id`，而 id 是**跨作品全局自增**，`_resolve_ids` 按本书 max+1 猜出来的号随时可能撞上同一条提案上一步刚插入的那一行。所以 writer 里 key 为 `?` 的记录一律 `row = None`——它是创建，去查表就是把创建读成改档。`_write_arcs` 与通用的 `_write_book` 同一条口径（人物卡同源，见 35.5）；`test_two_arcs_appended_in_one_proposal_do_not_land_on_the_same_key` 用「中间插一本别的作品的弧」把这个漂移钉住。
- **改道出来的弧认档**：`arc_proposal_from_toc_ranges` 把范围标题变成记录之前先看全书——起止章与档上某条完全相同就是**同一条弧**，只把围栏自带的 `标题/目标` 写上去，空值一律不许清掉档上的字；不相同才追加。凭据还是 D-43 那一条（起止章），做在抽取侧是因为卡片文本要**整份文件都对**才收得起，等 `_align_arc_history` 去绑已经晚了。
- **绑定不再靠块数算式**：`_align_arc_history` 原先要求「编号记录数（加上可绑的 `弧 ?`）＝档上记录数」，而一条纯追加的围栏**天生不满足这个算式**——它不打算重列全书。改成三步：`弧 ?` 先按起止章绑，绑上的把标题改写成档上那个号（`?` 会一路骗到 `_resolve_ids`）；位置兜底只在「编号记录数＝绑定后剩下的档上记录数」时允许；仍然对不上的编号记录整段放弃，删除由校验器说清楚。
- **跨号前缀整段去掉**：`_ARC_TITLE_PREFIX` 原来只吃 `弧 9：`，遇到 `弧 9-13：永恒的相对` 就剩下 `-13：永恒的相对` 当标题；锚点扩成 `弧 N` 与 `弧 N-M` 两种写法。
- **与判据原句的差异**：35.2 原句写「含范围标题的提案在生成阶段就被拒并触发一次有界自修复」。实现是**生成阶段改道**——不拒绝、不自修复、不多花一次模型调用，范围标题直接成为 C 层记录，B 层章号一寸不动。比原句省一轮，也不留「改完还红着」的中间态。
- **依据（真机 A/B，同一份围栏、同一份库副本、只换代码）**：HEAD 那台（8031）点应用 → PUT 发出 → 上面那句 422，弧数仍是 2；修好的那台（8033）点应用 → PUT 200 → 弧由 2 变 9（新 7 条起止章 11-30…301-500，标题「永恒的相对」无残留），章号集合应用前后都是 `[1..10]`，刷新后这条围栏**一张卡都不剩**（收起，不是红）。

### D-45 折叠控件钉在它折叠的内容之上；「展开后没法收起」是几何问题，不是状态问题

状态：生效。批次 35.3 裁定。主人报「提案展开后没法再收起」。量下来这句话两半都不假，可错的不是逻辑：双向那颗钮自 `c978ce3` 起就是 `setShowAll((value) => !value)`，`ProposalCard.test.tsx` 也钉着展开→收起两向——**但它在 `.proposal-diff` 这个纵向列表的末尾**，展开时它上面凭空多出 42 行，于是它自己被推走。主人说的「没法收起」是「看不见收起」，控件在不在屏幕外，jsdom 永远量不出来。

### D-46 写入落地的反应先重读章节清单，再取所选章记录；树只读 `chapters`

状态：生效。批次 35.4 裁定。主人报「说『创建第一章，先写简报』，应用之后左侧还是『还没有章节』，非要手动刷新」。真机量的：点「应用提案」后 `PUT /api/novels/6/files/chapters/0001/brief.md` 返回 200、`GET /chapters` 立刻是 1 条——**服务器已经改对了，界面没去再看一眼**。

- **为什么原来那次刷新是空的**：编辑面板对「写入落地」这个事件的反应调的是 `loadChapterRecords()`，它取的是所选章的生成记录与评审，左树一个字段都不读；而它内部还有一条硬规矩——**清单里落不了位的章节直接不取**（防跨书串档），所以「第一章刚被创建、清单还是空的」这一种情况它连请求都不发。两件事叠起来：该重读的没重读，读了的也没读。
- **裁定**：新增 `workbench.reloadChapterList()`，它是「树的两份来源」（`/planning/briefs` + `/chapters`）唯一的重读入口，跑完再 `await loadChapterRecords()`——**顺序是这条决定的正文**：清单先到，记录才可能落位。后台重读**不许动选择**（`selectedChapterId` / `selectedBriefId` 一律不写），主人当时可能正看任何一个文件。
- **否掉的修法**：应用成功后在前端自己拼一行章节塞进 `chapters`（等于在客户端造一份第二真源，D-02 直接顶回来）；或给新章自动开标签、自动跳过去（那是替主人决定他在看什么，且判据只要求树里出现第一章）。
- **断言搬家（D-33）**：`uiInvariants.test.ts` 新增「a landed write re-reads the chapter list before its records」，钉面板源文件里 `void reloadChapterList()`、不再出现 `void loadChapterRecords()`，并把 store 里这段动作切出来断言 `set({ briefs, chapters })` 在前、`await get().loadChapterRecords()` 在后、且整段不含 `selectedChapterId`。原「re-reads the chapter records once a proposal has landed」一例**未删**，改写成这条链的完整版（清单两次 GET + 记录一次 GET + StrictMode 双跑不刷新）。
- **门禁**：前端 277 passed、`tsc -b --force` 退出 0、`npm run build` 通过、命中区审计 small 0 / clipped 0 / unreachable 0（与 D-45 同一份 2 条 edge + 1 条 srOnly）；后端 375 passed（本条未碰后端）。
- **真机复测（8035 + `i354.db`，0 章作品）**：应用前 `{chapters:0, treeRows:9, 还没有章节:true}` → 点「应用提案」**不刷新** → `{chapters:1, treeRows:12, 还没有章节:false}`，与手动刷新后的快照逐项相同；四个标签逐个 HTTP 200，没有指向不存在文件的标签。
