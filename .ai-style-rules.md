## Naming and state-control rules

- Keep imports first, local types/constants next, pure helpers next, then the component/service and small handlers near their call site.
- React state names describe the visible concept (`rightView`, `chapterDelete`); refs describe cross-render control (`abortRef`, `draftStreams`).
- Preserve per-novel UI state across route and tab changes. Reset only when switching/deleting/invalidation makes the previous state unsafe.
- Route components compose; stores own multi-slice reloads; `api.ts` owns HTTP. Do not fetch directly in pages or components.
- Backend routes validate transport shapes and delegate. Writes use the canonical command handler when migrated and commit once.
- Errors shown to users are short and actionable. Tests assert behavior and data safety, not incidental implementation strings.
- UI uses existing tokens, 1px borders, compact rectangular controls and the established VSCode/Codex density.

## DONTs

- Do not introduce promotional AI cards, decorative gradients, oversized radii or pill controls without an existing exemplar.
- Do not add a UI filter or action before its backend state transition, recovery path and ordering semantics exist.
- Do not hide a featured record from the ordinary list unless the user explicitly requested deduplication.
- Do not create a second fetch layer, database write path, prompt copy or context builder.
- Do not replace measured editor/minimap geometry with guessed constants or browser-only visual assumptions.
- Do not treat passing unit tests as browser acceptance; take and inspect real screenshots after visual changes.
- Do not broaden adjacent refactors while fixing one feedback item.
